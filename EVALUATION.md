# Evaluation methodology

Evaluation is a first-class part of DocVerify. One command runs the full pipeline over a
version-controlled golden dataset and reports extraction quality and policy correctness
separately. It compares the run with a stored baseline and exits nonzero when a critical
threshold fails.

```bash
python -m app.evals.run --dataset data/golden                      # mock extractor (offline)
python -m app.evals.run --dataset data/golden --update-baseline    # store baseline
python -m app.evals.run --dataset data/golden --fail-on-regression # CI gate (exit 2 on regression)
python -m app.evals.run --dataset data/golden --provider openai    # live LLM (needs OPENAI_API_KEY)
```

Exit codes: `0` thresholds passed, `1` a critical threshold failed, `2` regression vs
baseline (with `--fail-on-regression`), `3` configuration error (for example a missing API key).

Outputs: `reports/<eval_run_id>_<provider>.json` (machine-readable), `reports/latest.json`
(served by `GET /evals/latest`), `reports/latest.md` (readable summary), and with
`--update-baseline` `reports/baselines/<provider>.json`. Every report records the eval run
ID, provider, model, prompt version, schema version, policy version, dataset version and
SHA-256, git commit, and duration.

## Golden dataset

`data/golden/cases.jsonl`: 50 cases, 108 documents (TXT and text-layer PDFs), generated by
`scripts/generate_golden_dataset.py`.

* **Where labels come from.** Expected field values are the facts the generator prints on
  each synthetic document. Expected outcomes, expected failed rules and the reason for each
  case are written by hand in that script. Nothing in the labeling path calls the
  extractor, calculations or policy engine, so labels are never produced by the system
  under test.
* **Integrity.** `manifest.json` stores the SHA-256 of `cases.jsonl`. A regression test
  fails if the dataset changes without regenerating the manifest. A dataset hash change is
  flagged in the baseline comparison as a non-comparable run.
* **Coverage.**

| Category | Cases | Examples |
|---|---|---|
| clean | 10 | weekly/biweekly/semimonthly/monthly, PDF, bank corroboration, employer suffix variants |
| missing_fields | 8 | no letter, no stub, missing gross, missing period, missing frequency, stale stub, letter without salary (optional) |
| conflicting_information | 5 | salary conflict, employer mismatch, name mismatch, two letters disagree, deposits don't match net pay |
| implausible_dates | 6 | reversed period, future pay date, 30-day "weekly" period, future start date, YTD < gross, net > gross |
| duplicate | 2 | byte-identical upload; same stub as TXT and PDF |
| variable_income | 3 | commission, per-assignment contractor, variable weekly hours |
| malformed | 4 | garbled text, corrupt PDF, scanned PDF without text layer, whitespace-only file |
| ambiguous | 2 | "approximately $85,000 total compensation" (not base salary), `09/10/2026` pay date |
| misleading_text | 3 | promo amounts and salary band, outdated starting salary, large non-payroll credits |
| prompt_injection | 3 | instructions in a stub, fake "Assistant:" turn in a letter, instruction in a bank transaction |
| policy_threshold / employment_status / currency | 3 | below income threshold, terminated employment, USD |
| free_form_layout | 1 | pay advice written as an email |

Expected outcomes: 16 APPROVE, 26 REFER_FOR_REVIEW, 8 INSUFFICIENT_EVIDENCE.

## Two policy evaluations

1. **End-to-end:** real extractor → normalization → calculations → policy. This measures
   what a user would experience.
2. **Gold extractions:** labeled fields are fed directly into calculations and policy.
   This isolates rule logic from extraction error. It should be 100%; any miss is a
   policy bug or a labeling bug, never an extraction problem.

The gap between the two numbers tells you how much outcome error the extractor causes.

## Comparison rules

* Money: canonical `Decimal` equality to the cent (`3076.9` equals `3076.90`; `3076.92`
  does not equal `3076.93`).
* Dates: ISO `YYYY-MM-DD` equality after parsing.
* Enums (frequency, status, currency, document type): exact canonical value.
* Names: case-insensitive after collapsing whitespace and stripping trailing `.`/`,`.
  Spelling differences remain errors.
* Null vs value is a mismatch in both directions: a hallucinated value where the label is
  null counts against the extractor exactly like a missed value.
* Fields are scored against the **expected** document type's field set, so a
  misclassified document loses all its field rows.

## Metric definitions

### Extraction
| Metric | Numerator / denominator |
|---|---|
| per-field exact-match accuracy | matching (document, field) pairs / pairs for that field |
| overall field accuracy | matching pairs / all applicable pairs |
| field-weighted score | Σ weight·match / Σ weight (critical fields weight 2, others 1) |
| critical-field error rate | mismatched critical pairs / critical pairs |
| missing-field detection rate | pairs with null label where extractor returned null / pairs with null label |
| unsupported value rate | pairs with null label where extractor returned a value / pairs with null label |
| present-field recall | pairs with a labeled value where extractor returned any value / pairs with a labeled value |
| money exact-match rate | money pairs equal to the cent / money pairs with a labeled value |
| money MAE | mean absolute error over money pairs where both values are non-null |
| deposit precision / recall | correct (date, amount) deposits / extracted, and / labeled |
| classification precision / recall / F1 | per class over documents; macro F1 averages classes with support |
| per-document-type accuracy | matching pairs / pairs, grouped by expected type |

### Policy
| Metric | Numerator / denominator |
|---|---|
| outcome agreement | cases whose outcome equals the label / all cases |
| rule-level agreement | (case, rule) pairs where FAIL vs not-FAIL equals the label / cases × rules |
| false approval rate | cases output APPROVE whose label is not APPROVE / cases whose label is not APPROVE |
| incorrect escalation rate | cases output REFER whose label is not REFER / cases whose label is not REFER |
| missing-evidence detection rate | cases labeled with a failing evidence rule (R001, R002, R012) where at least one such rule failed / those cases |

A case **passes** when its outcome and its exact set of failed rules both match the label.

### Derived
Recurring income agreement means cases whose annualized income equals the label to the
cent, with both null counting as agreement. Income pattern agreement means
RECURRING/VARIABLE/UNKNOWN equals the label.

## Critical thresholds (`data/golden/eval_thresholds.json`)

| Metric | Bound | Why |
|---|---|---|
| end-to-end false approval rate | ≤ 0.0 | Approving a case that should not pass is the costliest error |
| end-to-end outcome agreement | ≥ 0.85 | Overall usefulness |
| gold-extraction outcome agreement | ≥ 1.0 | Policy logic must match the labels exactly |
| gold-extraction rule-level agreement | ≥ 1.0 | Every rule, not only the final outcome |
| classification macro F1 | ≥ 0.90 | Misclassification cascades into everything downstream |
| critical-field error rate | ≤ 0.10 | Critical fields drive the rules |

## Baseline comparison

The current run is compared with `reports/baselines/<provider>.json`:

* Headline metric deltas (tolerance 0.005), with direction awareness (an error rate rising
  is a regression).
* Per-field accuracy drops greater than 1 point.
* Newly failing cases (passed in the baseline, fail now) with their rule diff, and newly
  passing cases.
* Metadata changes (prompt, policy, model, dataset hash), so a regression can be attributed
  to its cause. Runs with a different provider or dataset hash are marked non-comparable.

Example from development: setting `salary_tolerance_pct` to 1.00 in an experimental policy
made GC008 (2.44% variance) newly fail. Both gold-extraction thresholds failed and the command
exited 1. This is the intended guardrail for policy changes.

## Current results (mock mode)

> These numbers measure the **deterministic rule-based mock extractor**, not an LLM. The
> regex extractor was written alongside the document templates, so its high accuracy on
> templated documents is expected and says nothing about LLM quality. Its one systematic
> failure, the free-form email pay advice (GC050), is the kind of document that motivates
> an LLM extractor.

Run `eval_20261027T013757Z_e02ee3` (stored as `reports/baselines/mock.json`):

* Cases passed: 49/50. The failure is GC050, which was not classified, giving REFER instead of APPROVE.
* Overall field accuracy 98.8% (806 pairs), field-weighted 98.7%, critical-field error rate 1.3%.
* Missing-field detection 100%, unsupported value rate 0%, money exact match 98.4%.
* Classification accuracy 99.1%, macro F1 0.970.
* End-to-end: outcome agreement 98.0%, rule-level 99.7%, false approval 0.0%, incorrect escalation 4.2%, missing-evidence detection 100%.
* Gold extractions: 100% on every policy metric.

## LLM mode

`--provider openai` runs the identical harness with `OpenAIExtractionProvider`. No LLM
metrics are included in this repository because none have been measured yet. Run
`make eval-llm` with a key and store the result with
`--provider openai --update-baseline`. Expected discussion points: free-form layouts (GC050)
should improve, while injection cases (GC044–GC046) and ambiguity cases (GC039, GC040) test
whether the model follows the "null, don't guess" contract. Grounding failures show up as
`EVIDENCE_NOT_GROUNDED` issues and lower present-field recall.

## Model confidence

The OpenAI provider records the model's self-reported confidence per field as
`model_confidence`. It is stored and displayed but **not used in any rule**. It is not a
calibrated probability. Measured extraction accuracy from this harness is the only accuracy
claim. A natural extension is a calibration table: accuracy bucketed by reported confidence
over the golden set.

## Limitations

* Synthetic, template-generated documents are far cleaner than real documents. Accuracy
  here does not transfer to real-world documents.
* 50 cases give coarse metrics. One case moves outcome agreement by 2 points.
* Labels were written by one author. There is no inter-annotator agreement.
* LLM runs are not perfectly deterministic even at temperature 0. Compare LLM runs over
  repeated trials before treating a small delta as a regression.
